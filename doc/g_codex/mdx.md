## 1. 项目前期
- IDEA.md - 记录想法 (这里强调一下，IDEAS.md 是给自己看的账本，是对项目想法的记录，不是 OMX 的流程，所以要手动维护。)
- skill维护IDEA.md
- AGENT.md - 开发约定

> 新建 `mdx-editor` 文件夹，从该文件夹启动codex

> 根目录运行一次 /init 生成或整理 AGENTS.md，不要沿用前一个练习项目的文件。之后每次开工，Codex 都会重新读取它，后面的规划和开发按这份约定来。
```text
本项目开发约定:
0. 文档先行:引入库或框架前,先用 Context7 查对应版本的官方文档,避免使用过时的 API 和写法;
1. 测试先行:每一小块,先把验收场景写成会失败的测试,再写实现,测试全绿才算完成;
2. 函数不超过 50 行,单文件不超过 300 行,超了就拆。
```

1. 这些想法记进项目根目录的 IDEAS.md。
它是一本活账，记录当前版本准备讨论什么、暂时不做什么，也留住以后可能再考虑的想法。
想做的每条带上来历，暂时不做的写明原因。
这里的内容是访谈前的候选范围，后面的需求澄清会把它逐条确认，访谈结束后的需求说明才是第一版的最终范围。

2. 把 IDEAS.md 的维护方法做成 Skill
- 在 Codex 会话中调用 skill-creator，说明文件位置、用途、固定格式、创建与修改时的边界。
```text
$skill-creator 在当前项目创建一个名为 ideas-md 的项目级 Skill，这个 Skill 专门创建和修改项目根目录的 IDEAS.md。

上下文：IDEAS.md 是项目范围的活账，记录当前版本决定要做和暂不做的事项，也保留后续版本可能考虑的想法。后续需求澄清会读取它，作为本版范围基准。

格式固定为 # IDEAS、## 第一版要做、## 暂不做，顺序不变。第一版要做下面先用一段话概括完整交付闭环，再列出事项；每条要做事项说明来源或要解决的问题，每条暂不做事项说明当前不做的理由。

创建时，从用户明确说过的内容整理要做事项、暂不做事项和理由。修改时，先读取现有 IDEAS.md，保留来源与理由；新想法默认放进暂不做，只有用户明确纳入本版时才移入第一版要做。不要把完整需求说明、AGENTS.md 约定、代码实现或测试计划复制进账本。信息不足时指出需要用户决定的范围，不要替用户拍板。

创建后先校验 Skill 的结构，根据项目背景创建 IDEAS.md。写清了触发场景、固定格式、创建流程、修改边界和完成检查。
```

## 2. 引入工作流引擎 - OMX（oh-my-codex）
- 它是一个包在 Codex 外面的工作流引擎，把长任务分成几个阶段，每一步留记录，断了可以从记录继续，错了可以按阶段重新执行。
- 个人项目、中小型项目，这套工作流直接好用。项目再大、人再多，光靠它就不够了，需求中途会变，变了怎么对齐还得补流程（需求变更控制本身就是一个非常复杂的流程）。

> 为何需要工作流引擎？
- 引擎图的是“可控”，让模型在事先说好的范围里输出，每步要什么、产出什么、怎么验，先定好。不是许愿式编程

> 复杂长任务的三个麻烦
1. 会话断了怎么办：聊了几百条消息，换个会话 Codex 就不记得之前干到哪了；
2. 做到哪算哪：没有地方写着“现在做完了几步，还剩几步”；
3. 出问题怎么回头：改了三天发现方向错了，想不起当时计划长什么样。

> 四个工作节点
- “需求→设计→编码→测试”，在这套流程里对应三个自动节点和一道人工放行关卡。前三个节点由 OMX 调度，人工验收由开发者完成。

### 安装OMX
```text
检查我的系统是否具备运行 oh-my-codex 的条件。确认操作系统、Node.js、npm、Git,以及 tmux(Windows 是 psmux)的版本。然后帮我安装好，如果需要我来确认或者安装，告知我如何操作。
```

- 安装完成后验证：
```cmd
omx --version
omx doctor
```
两条命令都能运行，再在当前项目根目录启动一次 omx，确认能进入 Codex 并读到项目里的 AGENTS.md。

## 3. omx 开始工作
- deep-interview  聊想法
- replan 讨论方案（规划，架构，挑刺）
- ultragoal OMX自己跑

### 第一步：想法问明白 - deep-interview
- 将markdown的渲染参考提供给omx,使用$deep-interview 让它提问

```text
$deep-interview 我要开发一个本地 Markdown 编辑器,自己用。
想法、来历和第一版的范围都记在 IDEAS.md 里,先读一遍再开始问。
预览的渲染基准在 docs/markdown渲染规格参考.md。
全程用中文,整理出的需求说明等文档必须用中文写。
```

- 回答问题时少说行容器，比如“体验要好”没法执行，下面这样才行：
```text
1. 我从本地选一个工作目录,目录树里能看到 Markdown、HTML 和图片。点图片可以预览。
2. 编辑后想切换文件,先处理没保存的修改;我选取消的话,文件和内容都保持原样。
3. 独立预览窗口最多开一个,再点一次就把已有的窗口调到前面。
```

### step2: 聊方案 - ralplan 
> ralplan 安排三个角色，把方案轮流讨论清楚。
- Planner（规划）：把需求拆成一步步能做能查的小块，比较几个可行方案；
- Architect（架构）：看结构有没有隐患，几个模块的责任分得清不清；
- Critic（挑刺）：专门找茬，这个方案哪里会挂？验收标准漏了什么？

`启动 ralplan:`
```text
预览的渲染规格和验收样例在 docs/markdown渲染规格参考.md,选型和测试规格对照它写。
全程用中文,产出的方案文档和测试规格必须用中文写。
只生成方案文档和测试规格,不要修改需求范围,不要写实现代码。
```
